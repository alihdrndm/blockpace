# M5 walkthrough: the dashboard

## What was built
`apps/web` is a Next.js App Router dashboard with the five pages from the spec. `/` lists every room block with today's risk badge, pickup, shortfall, the amount owed today and the amount projected at cutoff. `/blocks/[id]` shows one block: seven tiles, a pace chart, the nightly table, a "Record snapshot" form, a CSV import and the block's alerts. `/blocks/new` creates a block from a grid generated from the first night and the number of nights. `/calculator` evaluates a contract without saving it, on both bases side by side. `/webhooks` manages webhook endpoints and lists the latest deliveries. A Playwright smoke test walks the spec's happy path against a seeded stack.

## Design decisions
1. **The browser never talks to the API.** Pages are server components that call the API through `src/lib/api.ts`; forms use server actions (`src/app/actions.ts`) and the calculator posts to the route handler `app/api/calculate`. The API key and the API address stay on the server.
2. **The same schemas everywhere.** API responses are parsed with the Zod schemas from `packages/core`, so a contract change breaks the build instead of the page. Errors arrive as problem+json and every view shows their `title` and `detail` in place, so one failing call does not blank the whole page.
3. **Accessible by construction.** Every input has a label, the risk badge pairs colour with text and an icon, the chart has a "Show data" table, and numbers use tabular figures. Money is always formatted from minor units with `Intl.NumberFormat`.

## Read first
- `apps/web/src/lib/api.ts` (the typed API client) and `src/lib/format.ts` (money, dates, badges).
- `apps/web/src/app/blocks/[id]/page.tsx` (how one page loads several API calls and degrades per section).
- `apps/web/src/app/actions.ts` (server actions behind every form).
- `apps/web/e2e/smoke.spec.ts` and `playwright.config.ts` (how the real stack is started for the test).
