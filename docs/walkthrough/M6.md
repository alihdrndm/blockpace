# M6 walkthrough: packaging, infrastructure and docs

## What was built
The project now runs the same way everywhere. Each app has a `Dockerfile` (`apps/api`, `apps/worker`, `apps/web`), and `compose.yaml` starts the whole stack: PostgreSQL, the API (which runs the migrations on start), the worker, the web dashboard, a one-shot seed that loads the three demo blocks, and the webhook sink that prints `signature OK` for every signed webhook it receives. `sst.config.ts` and `infra/*.ts` describe the same system on AWS, ready to deploy but never deployed. The repository also gained the documents an open-source project needs: README, CONTRIBUTING, SECURITY, CHANGELOG, ARCHITECTURE and a deploy guide.

## Design decisions
1. **Build once, ship only what runs.** Each Dockerfile builds the shared packages and the app in one stage, then copies only production dependencies (`pnpm deploy --prod`) and the build output into a slim image that runs as the unprivileged `node` user. The image is smaller, and a compromised app has fewer rights.
2. **Containers on AWS, not Lambda functions.** SST bundles Lambdas with esbuild, which drops the decorator metadata NestJS needs. Running the API and worker as Fargate containers, built with the same Dockerfiles as local development, avoids that and means what you test locally is what would run in AWS.
3. **Costs are written down, not estimated.** `docs/DEPLOY.md` lists every AWS resource and says which ones bill while they exist (database, Fargate tasks, load balancer, NAT instance), with links to the pricing pages, so nobody is surprised.
